Basic AI Flow

English · 日本語 · テキスト版ガイド

backend（Go）、admin（Next.js）、mobile-app（Flutter）を横断する AI フローです。ai-flow-demo 直下から、1 回に 1 ステージずつ実行し、必ず承認で止まります。

コマンドは 1 つだけ

コマンド動作
/aiflow PROJ-XXXXチケットの次のステージを実行して停止。新規チケットはステージ 1 から。
/aiflow全チケットの一覧（ステージ・ルート・リポジトリ・次の手順）。
/aiflow PROJ-XXXX status進捗と、ステージごとの時間・トークン・概算コスト。
/aiflow PROJ-XXXX featureバグ修正ではなく新規開発（feature/… ブランチ）として開始。
/aiflow PROJ-XXXX redo specステージのやり直し（ticket spec plan impl review deliver）。
/aiflow analyze · /aiflow wikiナレッジグラフ更新（無料）· アーキテクチャ Wiki 作成（トークン消費あり）。
/aiflow <PR/MR の URL>既存の PR/MR をレビュー。

6 つのステージ

1 · チケットNotion 取得、bug/feature 判定、影響リポジトリ、難易度判断、ブランチ作成
承認
2 · 仕様原因分析または設計
承認
3 · 計画TDD タスク（1 タスク 1 リポジトリ）
full のみ・承認
4 · 実装タスクごとに実装・仕様レビュー・品質レビュー
5 · レビューリポジトリ横断の最終レビュー＋テストケース
full のみ
6 · デリバリーテスト、手動 QA、Draft の PR/MR、CI 指摘の修正、その後 Ready
QA・承認

light 1 → 2 → 4 → 6。次をすべて満たす場合のみ：1 リポジトリ、3 ファイル以内、API/スキーマ/DB 変更なし、原因特定済み、バグである、センシティブ領域（課金・認証・マイグレーション）ではない。ステージ 1・2 は 1 ターンで、承認も 1 回。

full それ以外は 6 ステージすべて。ルートは引き上げのみで、黙って下げることはありません。各ステージは停止するので、結果を確認してから再度 /aiflow PROJ-XXXX を実行します。

成果物は docs/aiflow/<ID>/：ticket.md、spec.md、plan.md、reviews/、test-cases.md、status.md（進捗。次のステージ判定に使う唯一のファイル）、log.json（時間・トークン・コスト）。

必須ルール

main へ直接 push しないベースブランチへの反映は PR/MR のみ。develop/main へのコミットも force-push も禁止。
機密情報は commit しないキー、トークン、パスワード、.env*、認証情報ファイルは stage も push もしません。commit のたびに git diff --cached を確認します。
GitHub/GitLab への書き込みは毎回確認git push、PR/MR の作成・編集、コメント投稿が対象。操作内容・対象・投稿する本文を提示し、明確な承諾があったときだけ実行します。以前の承認、QA の回答、設定フラグでは代替できません。PR/MR の merge・approve・close は自動では行いません。
レビュアー名を記録すべてのレビューと承認に human:<名前> または ai:<役割> (<モデル>) を、reviews/*.md、status.md の承認欄、PR コメントに残します。
全リポジトリで同じチケットブランチチケットが開いている間、ラッパーと影響を受ける全リポジトリが同じ bug/PROJ-XXXX/… または feature/PROJ-XXXX/… ブランチにいます。

PR/MR テンプレート

タイトルに Notion のタスク ID（例：[PROJ-123] …）を含め、タスクと連携します。本文はチームの見出しをそのまま使います。

見出し内容
概要この PR で何をなぜ変えたか。関連 PR と spec/plan/レビューへのリンク。
スクリーンショットUI 変更の前後画像。変更がなければその旨を記載。
相談項目レビュアーに聞きたい点（Minor の指摘を含む）。なければ「なし」。
動作確認手順レビュアーが再現できるように：端末、手順、結果。未確認の範囲も正直に記載。

デリバリーの順序（ステージ 6）

1. 各リポジトリのテストを実行
2. QA ゲート         → 「確認済み、PR を作成」（push の承諾ではない）
3. 確認              → <repo> の <branch> を origin へ push？
4. 確認              → PR/MR を DRAFT で作成（タイトル、base ← head、本文全文）
5. CI レビュー実行   → /aiflow <ID> を再実行：CI の指摘を 1 件ずつ修正または回答
                       （push・返信は毎回確認）、未対応が 0 になるまで
6. 確認              → Ready for review に変更 → 顧客がレビュー
7. merge             → チャットで依頼したときのみ

ラッパーを含む各リポジトリは、/aiflow setup で選んだホストに応じて gh（GitHub）または glab（GitLab）を使います（pr.tool / pr_tool）。

フローの更新

スキルとルールは汎用の harness-ai-flow バンドルから提供されます。変更はそちら（README も同時に）で行い、ここでは install.sh --force で再インストールします。.claude/skills/ の直接編集は上書きされます。プロジェクト固有の設定は aiflow/workflow.yaml のみ。

任意: aiflow-visual はブラウザ補助（モックアップや図を表示するローカルページ）です。各ステージは視覚的な質問のときだけ、同意を得てから提案します。テレメトリは無効で、.superpowers/ は git に含めません。
