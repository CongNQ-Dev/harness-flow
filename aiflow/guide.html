Triage · 難易度判断

省略版と完全版

Light route and full route

ステップ1の最後にAIが根拠付きで判定し、あなたが確定します。簡単なチケットは軽量モデル＋省略版でAI利用料を抑えます。省略版が確定した小さな不具合は、その場（ステップ1の実行中）で根本原因を調査して仕様まで書いてしまいます — 対話は挟みません。調査中に複雑さが判明したら自動で完全版に切り替わります。

At the end of stage 1 the AI proposes a route with evidence, and you confirm it. Simple tickets use a cheaper model and the light route to keep AI costs down. A small bug confirmed as light gets its root cause investigated and its spec written right there, during stage 1's run — no dialogue. If that investigation finds more complexity, it switches to full automatically.

省略版Light1+2（1回で）→ 4 → 61+2 (one run) → 4 → 6

  • 1リポジトリのみ
  • 変更ファイル3以下
  • API・GraphQL・DB・契約の変更なし
  • 原因箇所を特定済み（file:line）
  • 不具合対応（新規開発ではない）
  • 課金・認証・引継ぎ・DB に該当しない
  • One repo only
  • 3 files or fewer
  • No API / GraphQL / DB / contract change
  • Root cause located (file:line)
  • A bug, not new development
  • Not billing, auth, account transfer or DB

完全版Full1 → 2 → 3 → 4 → 5 → 6

  • 上記のどれか1つでも満たさない場合
  • 判断できない項目がある場合（「不明」は完全版扱い）
  • 複数リポジトリにまたがる不具合
  • 新規・保守開発
  • Any light condition not met
  • Anything that can't be determined ("unknown" counts as full)
  • Bugs spanning several repos
  • New or maintenance development
One flow · three repos

3リポジトリを1つのフローで

Three repos, one flow

フローは ai-flow-demo リポジトリだけにあり、ソースコードのリポジトリにはコピーを置きません。横断ナレッジグラフが backend の型とアプリ・管理画面側の型をつなぎ、片側だけでは直らない不具合も両側まとめて扱えます。

The flow lives only in the ai-flow-demo repo; the source repos carry no copy. The cross-repo knowledge graph links backend types to their app and admin counterparts, so a bug that needs both sides is handled as one ticket.

  • ステップ1で影響リポジトリを判定し、全対象リポジトリに同名ブランチを作成（例: bug/PDT-1107/fix_season_tab_filter）。
  • 実装順はAPI提供側が先。backend のスキーマ変更 → admin/アプリのクライアント再生成 → 画面側の修正。
  • 最終レビューはリポジトリ横断で、APIの項目・型・後方互換性の食い違いを検出。
  • PRはリポジトリ毎に作成して相互リンク。各チームのルール（例: bump-mobile-app の CLAUDE.md・docs/ai/・bump-* スキル）を優先して守る。
  • Stage 1 finds the affected repos and creates the same branch in each (e.g. bug/PDT-1107/fix_season_tab_filter).
  • The API owner goes first: backend schema change → regenerate the admin/app clients → screen changes.
  • The final review covers all repos and catches mismatched fields, types and backward-compatibility breaks.
  • One PR per repo, all linked to each other. Each team's own rules win for code, e.g. bump-mobile-app's CLAUDE.md, docs/ai/ and bump-* skills.

AI利用料はどこで見られる？status.md があるのに log.json も必要？Where do I see AI usage cost? Why log.json when status.md already exists?

/aiflow PDT-XXXX status で、ステップ毎の所要時間・トークン数・概算料金（API換算）を表示します。記録は docs/aiflow/PDT-XXXX/log.json。難易度判断の閾値調整に使います。

この2つは別の軸を記録しているので、片方がもう片方の代わりにはなりません。status.md は「どのステージまで終わったか・誰が承認したか」という進捗で、/aiflow が次に何を実行するかを判断するのはこれだけです。log.json は「そのステージにどれだけ時間・トークン・費用がかかったか」という利用量で、進捗判断には一切使いません。「省略版は本当に完全版より安いか」「どのステージが一番コストがかかっているか」に答えるためのもので、ご提案書の「AI利用料の最適化・低減の加速」に対応する記録です。

/aiflow PDT-XXXX status shows time, tokens and estimated cost (at API prices) per stage. The data is in docs/aiflow/PDT-XXXX/log.json and is used to tune the triage thresholds.

The two track different axes, so neither substitutes for the other. status.md is progress — which stage is done, who approved it — and it's the only thing /aiflow reads to route. log.json is usage — time, tokens, cost per stage — and never feeds routing. It answers what progress tracking can't: "is light route actually cheaper than full", "which stage costs the most" — the AI-cost-optimization requirement from the proposal.

不具合と新規開発、どうやって見分ける？How does it tell a bug from a new feature?

/aiflow PDT-XXXX feature と明示すれば最優先で feature になります。指定がなければ、まず Notion チケットの種別プロパティを見ます — 「不具合」「Bug」系の値なら bug、「新機能」「Feature」「新規開発」系の値なら feature。これが主な判断材料で、ticket.md の「種別」欄にそのまま記録されるので、後から確認もできます。種別が空・曖昧な場合は本文を見て、既存の壊れた挙動＋再現手順があれば bug、新しい望ましい挙動の説明だけなら feature と判断します。それでも決められない場合だけ、AIが1回質問します — 推測はしません。

/aiflow PDT-XXXX feature overrides everything. Otherwise the primary signal is the Notion ticket's 種別 (type) property — a defect-naming value (不具合 / Bug) → bug, a new/improved-behavior value (新機能 / Feature / new development) → feature — recorded in ticket.md's 種別 row as the evidence, so you can check it later. If 種別 is empty or ambiguous, the AI reads the ticket body: broken current behavior with repro steps → bug; only a description of desired new behavior → feature. It asks you, once, only if that still doesn't resolve it — never a guess.

wiki とナレッジグラフ、何が違う？なぜ wiki は自動更新しない？Wiki vs. knowledge graph — and why doesn't the wiki auto-update?

ナレッジグラフ（graphify-out/）は機械的な抽出です — コードのAST解析だけで、LLM費用がかからないので commit/checkout のたびに自動更新しても問題ありません。wiki（wiki/）はAIがコードを読んで文章を書くもので、実行するたびに本物のトークンを消費します。これが、グラフは /aiflow analyze で気軽に更新できるのに、wiki は /aiflow wiki を明示的に実行したときだけ生成・更新される理由です — git フックで自動化すると、commitのたびにAI費用が発生してしまいます。

初回生成のあとは自動で古くならないよう更新されません。チケットの仕様で本当に重要なアーキテクチャ決定があったときだけ、aiflow-spec が wiki/architecture/decisions/ に1件だけ追加します（そのチケットで既に調べた内容を使うだけなので追加コストはほぼゼロ）。コード全体を読み直したいときは /aiflow wiki refresh を手動で実行してください。

The knowledge graph (graphify-out/) is a mechanical extraction — AST analysis only, no LLM cost, so it's safe to auto-refresh on every commit/checkout. The wiki (wiki/) is the AI reading code and writing prose — it costs real tokens every time it runs. That's why the graph can be casually refreshed with /aiflow analyze, while the wiki is only generated or updated when you explicitly run /aiflow wiki — automating it via a git hook would mean AI spend on every commit.

After the initial write, it does not keep itself current automatically. When a ticket's spec genuinely records an architecture decision, aiflow-spec appends one entry to wiki/architecture/decisions/ — cheap, since it reuses that ticket's own investigation. Run /aiflow wiki refresh yourself for a full re-scan.

設定を変えたい（テストコマンド・ブランチ・判定条件）I want to change settings (test commands, branches, triage)

Everything is in aiflow/workflow.yaml. No need to edit the skills.

他のプロジェクトでも使える？ このリポジトリを clone しないと駄目？Can this be reused on another project? Do I have to clone this repo?

このフローは BUMP 専用に作られていません — .claude/skills/aiflow*/ のロジックはすべて aiflow/workflow.yaml からリポジトリ名・スタック・テストコマンドを読み取る作りで、スキル本文に直接書いていません（単一リポジトリのプロジェクトでも repos: に1件だけ書けば動きます）。

clone は不要です。プロジェクトのルートで install.sh を実行すると、このリポジトリを一時フォルダに clone → 必要なスキル・スクリプトだけコピー → 一時フォルダを削除、を自動でやります（harness-workflow builder の install.sh と同じ仕組み）。埋めるのはあなた自身です: aiflow/workflow.yaml.template をコピーして、あなたのプロジェクトのリポジトリ・スタック・テストコマンドを書き込みます。

This flow isn't built BUMP-only — every skill under .claude/skills/aiflow*/ reads repo names, stacks and test commands from aiflow/workflow.yaml, never hard-coded in the skill bodies (a single-repo project works too — just list one entry under repos:).

No clone needed. Run install.sh against your project's root — it clones this repo into a temp dir, copies only the skills and scripts, and deletes the temp dir (same mechanism as harness-workflow builder's own install.sh). You still fill in aiflow/workflow.yaml.template yourself with your project's real repos, stacks and test commands.

.claude/skills/ に aiflow- が付かないスキルがあるのはなぜ？Why do some skills in .claude/skills/ have no aiflow- prefix?

aiflow- で始まるものだけがステージ本体で、/aiflow から呼ばれます。test-driven-development・systematic-debugging・verification-before-completion・receiving-code-review・requesting-code-review・dispatching-parallel-agents・graphify の7つは、各ステージが状況に応じて内部的に読み込む汎用スキルです。プレフィックスをあえて付けず、/ メニューにも出しません（user-invocable: false）— /aiflow-* と名前が衝突しないのと、それぞれの説明文が「Use when…」で始まる標準形式で書かれていて、AIが状況を見て自動的に読み込む仕組みだからです。自分で直接呼ぶことはありません。

Only skills prefixed aiflow- are the stages themselves — what /aiflow calls. The other seven (test-driven-development, systematic-debugging, verification-before-completion, receiving-code-review, requesting-code-review, dispatching-parallel-agents, graphify) are generic engineering-discipline skills each stage loads internally when the situation calls for it.
